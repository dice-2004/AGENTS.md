## 進め方
- 回答・コメント・コミットメッセージは [日本語] で書く。
- あるモジュールの作業を始めるとき、このセッションでその仕様書（`[例: docs/spec/]`）をまだ読んでいなければ読む。会話が要約・圧縮されたあとは読み直す。
- 確認してから行う：[例: 仕様書のない新機能の実装、新しいファイル・モジュールの追加、外部パッケージの追加、公開インターフェースの変更、設定・インフラの変更]。確認では、どのファイルのどこを、なぜ、どう変えるかを説明する。
- 確認せずに行ってよい：[例: 既存関数内のバグ修正、テストの追加、コメント・命名の修正]。自分の変更が原因で検証中に見つかったバグの修正も含む。
- 同じエラーの修正を [3] 回試して直らなければ、止めて、試した内容・エラーログ・現状を報告する。
- 依頼の範囲外のファイルは変更しない（「記録」の節に挙げたファイルの更新は除く）。気づいた改善点は提案として報告する。
- 仕様や外部 API の挙動に確信がないときは、断定せずにそう書いて確認を求める。
- 【選択】仕様の不明点の扱い
  - A：仮定で進めず、質問にまとめる。
  - B：取り消せる作業は仮定を置いて進め、置いた仮定を報告する。
- 途中でユーザーに確認できない実行（クラウドのタスクなど）では、確認が必要な操作は行わず、報告か PR の説明に「提案・未実施」として書く。試行の上限に達したときは、そこまでの変更をブランチに残して状況を報告する。

- コードを変えて仕様（入出力、設計）が変わったら、同じ変更の中で仕様書も直す。

- [このプロジェクト固有の技術ルール。例: DB アクセスは `src/db/` 経由のみ。]

## Git

- B：作業ブランチへのコミットは行ってよい。作業ブランチが指定されている実行（クラウドのタスクなど）では、そのブランチへの push も行ってよい（push しない変更は残らないため）。それ以外の push と PR の作成は、依頼に含まれるときだけ行い、それ以外は確認する。`[main]` への直接 push、force push、履歴の書き換えは行わない。

## 守るべきもの
- このファイル（AGENTS.md）と CLAUDE.md は、ユーザーの明示的な指示なしに編集しない。改善案は提案する。
- 変更しない：[例: `vendor/`、`migrations/` の既存ファイル]
- 合意があるときだけ変更する：[例: 共有モジュール `src/core/`]
- API キー・トークン・パスワードを、コード・コミット・ログ・チャットに書かない。機密情報は [例: 環境変数] から読む。
- ファイルの削除、サービスの停止・再起動、DB の破壊的な変更（マイグレーション、レコード削除）、[本番・共有環境] への操作は、内容を説明して承認を得てから行う。できるものは先にドライランの結果を示す。

## 記録
- [進捗を記録する場合。例: 作業開始時に `docs/progress.md` を読む。サブタスクの完了・方針の決定・作業の終了前に、今の状態・決定事項・検証結果を更新する。]
- [前提知識のファイルを置く場合。例: 設計の決まりを変えたときと、今後も効く事実（外部 API の癖、試してだめだった方式）が分かったときに、`docs/context.md` を更新する。]
- [トラブルシューティングを置く場合。例: エラーが起きたら、まず `docs/troubleshooting.md` を確認する。載っていない問題を解決したら、原因と対処を追記する。]
- 記録ファイルの更新は、その作業と同じコミット・PR に含める。Git 操作を任されていないときは、更新した内容を報告に書く（クラウドの実行では、コミットしていない変更は残らないため）。

## 報告
完了時は次の順で報告する。
1. 変更内容
2. 理由・意図
3. 検証方法と結果（実施していなければ「未確認」）
4. 残課題・提案

## 指示の優先順位
- このファイルと会話中の指示が食い違うときは、会話中の直近の明示的な指示を優先する。ただし「Git」「守るべきもの」は、ユーザーがそのルールの一時解除を明示したときだけ外す。
- ユーザーの全体設定（個人設定など）とこのファイルが食い違うときは、このリポジトリについてはこのファイルを優先する。
- スキルの指示とこのファイルが食い違うときは、このファイルを優先する。
